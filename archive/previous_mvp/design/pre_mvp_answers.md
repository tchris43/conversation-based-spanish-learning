# Pre-MVP Decisions
These capture the agreed answers to the **[Before MVP]** questions so we can proceed with clarity before planning code.

1. **Success for the beginner persona:** After MVP the learner should be able to initiate and respond to basic greetings, ask for help, describe simple past/future events, name objects in their environment, and answer follow-up questions about a short, everyday scenario. Conversational fluency means handling 3–4 turn exchanges with growing confidence rather than grammar perfection.
2. **Onboarding flow:** Immediately on first use we collect the learner’s primary goal (e.g., “talk to coworkers”), available weekly practice time, preferred topics (travel, hobbies), and a quick self-rating (“brand-new”, “know a few words”) so the first session has direction.
3. **Progress profile storage:** Everything lives client-side (localStorage or IndexedDB). We persist exposures, correctness ratios, “needs work” tags, recent evidence phrases, and summary metadata (last practiced topic, streaks). The app reads/writes this structure before and after each session to keep context in sync.
4. **Target LLM/tooling:** Start with a single reasoning-capable OpenAI-style model (e.g., gpt-4o-mini, but we can swap via the single `callModel` abstraction). Prompts include the learner profile summary and current lesson so we stay under token limits, and we can throttle history to the top 5 items plus the current drill.
5. **Detecting “needs work”:** Use defined thresholds (e.g., 3 exposures with <60% correct usage) plus spaced-review windows; if the learner repeats errors at increasing intervals, we flag the concept again. Each flag records the phrase/turn that fired it to seed later drills.
6. **Storing rationale:** Require the LLM to emit a short, concrete reason for every “needs work” tag (e.g., “you kept swapping present tense for past tense twice”). Store that rationale alongside the trigger phrase and timestamp so the insight is auditable.
7. **Authentication/session:** MVP uses anonymous sessions tied to the same browser. We can generate a lightweight local learner ID and store it with the profile. No external auth required yet.
8. **Instrumentation/logging:** Capture prompt/response pairs, “needs work” decisions, and stored evidence in developer console logs/local diagnostics during early testing; additional logging can layer in later once we know what’s useful.
9. **Infrastructure constraints:** The web UI can be a static SPA hosted on a lightweight CDN; LLM calls go through a small proxy service to manage API keys. Keep latency low by caching summaries client-side and trimming conversation history before sending.
10. **Privacy/regulations:** Since all progress data stays local, we avoid centralized PII storage. We’ll inform users (via a simple notice) that clearing their browser will erase progress; no regulated data is collected in MVP.
11. **Prompt reliability:** If the LLM can’t cite a rationale or the rationale is vague, treat it as low confidence, log the incident, and defer tagging until we gather more evidence. We can also add a verification prompt asking the model to explain which turns support the insight before we store it.
12. **Content library:** For the MVP we rely on the LLM to generate conversational material from structured instructions and the learner profile. We don’t need a curated set of prompts yet; we can add authored templates later if the improvisational approach misbehaves.
